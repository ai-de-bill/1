# reduce_ascend — групповое суммирование int64 на Ascend 910B

Отдельный проект по образцу `mul_ascend` / `div_ascend`: сумма элементов `int64` по группам, где группы
заданы префиксными суммами и массивом индексов. Арифметика целочисленная, по модулю 2^64 (естественное
переполнение `int64`), без насыщения.

## Семантика

| Вход | Тип | Размер | Смысл |
| --- | --- | --- | --- |
| `x` | int64 | `T × M`, **column-major** | столбец `j` — непрерывный блок `[j*T, (j+1)*T)` |
| `idx` | int32 | `T` | `idx[k]` — номер строки `x`, которая становится `k`-м элементом группового порядка (перестановка `0..T-1`; это ровно `indices` из `index_ascend`) |
| `prefix_sum` | int32 | `G + 1` | группа `g` занимает `k ∈ [prefix_sum[g], prefix_sum[g+1])` |
| `y` | int64 | `G × M`, **column-major** | `y[g, j] = Σ_{k ∈ group g} x[idx[k], j]` (mod 2^64) |

**Последняя группа всегда доходит до `T`.** При канонических префиксных суммах это то же самое, что
`prefix_sum[G]`; но пример из задачи (`prefix_sum = 0,4,6,7` при `T = 8`) иначе терял бы `idx[7] = 6`.

Пример из задачи — `idx = 2,1,0,5,3,4,7,6`, `prefix_sum = 0,4,6,7`, `T = 8`, столбец из `1..8`:

| группа | `k` | строки | сумма |
| --- | --- | --- | --- |
| 0 | 0..3 | {2,1,0,5} | 3+2+1+6 = **12** |
| 1 | 4..5 | {3,4} | 4+5 = **9** |
| 2 | 6..7 | {7,6} | 8+7 = **15** |

## Алгоритм: точная 64-битная сумма из 16-битных половин

На 910B (`dav_c220`) нет 64-битной целочисленной векторной арифметики, поэтому сумма собирается из
четырёх точных 16-битных сумм. Для `v = hh·2^48 + hl·2^32 + lh·2^16 + ll`:

```text
sum(v) = (Σ ll) + (Σ lh) << 16 + (Σ hl) << 32 + (Σ hh) << 48
```

Суммирование идёт **по линиям вектора**: четыре аккумулятора (по одному на 16-битный чанк) накапливают
значения `Add`-ом, поэтому ни одна частичная сумма не переполняется: линия накапливает
`ceil(T / 512) ≤ 8` значений `≤ 0xFFFF` (< 2^19), а итог по 512 линиям остаётся < 2^28. Всё точно, ни UB,
ни сатурации.

Ядро, по одному столбцу за раз:

1. `DataCopyPad` — весь столбец `T × int64` в UB (одна копия);
2. для каждой группы — тайлы по `kTileK` значений `k`:
   * `DataCopyPad` тайла `idx` → `Muls(..., 8)` → байтовые смещения `idx[k]*8`;
   * `Gather` двух 32-битных половин элемента: младшая по базе `0`, старшая — по базе `4`;
   * `And` (16-битная `vand`) и `ShiftRight` по `uint32` → четыре 16-битных чанка, `Add` в аккумуляторы;
3. после последнего тайла группы: свёртка каждой линии в линию 0 (`Add`-дерево + три шага `Gather`+`Add`),
   сборка `lo`/`hi`, упаковка `[lo, hi]` и `DataCopyPad` 8 байт в `y`.

Сетка: `blockDim = 16` (`context->SetBlockDim(16)`), блок `b` берёт столбцы `j = b, b+16, b+32, …`.

## Только векторные инструкции

Скалярного пути больше нет: **каждая операция над данными — векторная или MTE (DMA)**.

| Шаг | Инструкции |
| --- | --- |
| `x` (столбец), `idx` (тайл), `y` (8 байт на группу) | `DataCopyPad` (MTE2 / MTE3) |
| `idx[k]*8` — байтовые смещения | `Muls` |
| выборка строк группы | `Gather` (младшее слово по базе 0, старшее по 4) |
| четыре 16-битных чанка | `And` (16-битная `vand`), `ShiftRight` по `uint32` |
| накопление по группам | `Add` по линиям (4 аккумулятора), без свёртки внутри цикла тайлов |
| свёртка линий (512 → 1) | `Add`-дерево до 8 линий + 3 шага `Gather`+`Add` по постоянным таблицам смещений |
| сборка int64 | `Gather` (broadcast линии 0), `ShiftLeft`/`ShiftRight`, `Add` |
| упаковка `[lo, hi]` и запись | `And` + `Add`, затем `DataCopyPad` |

`GetValue`/`SetValue` по данным не используются вообще; через `SetValue` пишутся только **константы**
(таблицы смещений и маски) один раз в `BuildTables`.

Скалярными остались исключительно **управление циклом**: `T`, `M`, `G` из tiling-буфера и две границы
группы из `prefix_sum` (номера `k`), плюс счётчики циклов — ни один элемент `x`/`idx`/`y` через скалярный
юнит не проходит.

Ограничение то же: векторный `Gather` работает по UB, поэтому весь столбец должен туда влезать —
`T ≤ kColBufElems = 4096` (32 КБ). Это проверяет `TilingFunc` и возвращает `GRAPH_FAILED` при `T > 4096`,
вместо того чтобы писать мусор.

### Найдено по факту прогонов

1. **`CheckTensorAlignment` в CPU-модели**: `Duplicate(lo[cnt], 0, …)` и `Add(v, v, v[len >> 1], …)` при
   шаге меньше 8 элементов (32 байта) валятся — модель требует 32-байтовые тензоры. Отсюда: нуление
   хвоста только по смещению `0`, дерево суммы до 8 линий, а последние три шага — `Gather`+`Add` по
   постоянным таблицам смещений (по 8 записей, чтобы шаг остался 32-байтовым).
2. **Сдвиги в AscendC есть только для `uint32`** (`ShiftLeft`/`ShiftRight` по `int32` не компилируются) —
   и это же даёт логический сдвиг без расширения знака.
3. **`DataCopyPad` требует совпадения типа**: для записи 8-байтового результата источник приводится к
   `int64` (`out.ReinterpretCast<int64_t>()`), иначе перегрузки нет.
4. **Сборка опа без `REGISTER_TILING_DEFAULT`** падает на `libascend_hal.so` (компилятору нужно загрузить
   `liboptiling.so`), поэтому в ядре оставлены inline-структура `ReduceAscendTilingData` и
   `REGISTER_TILING_DEFAULT` — ровно как в `mul_ascend`.
5. **Векторная запись одного int64 без скаляров**: сборка `[lo, hi]` делается как
   `And(lo, maskEven) + And(hi, maskOdd) + Add` (маски — 32-битные `0xFFFFFFFF`/`0`, читаются как 16-битные
   пары), после чего `DataCopyPad` пишет 8 байт в `y`.

## Следующие шаги

1. **Харнесс прямого запуска** (`test/direct_launch_check.cpp` + `build_direct_launch.sh`, копия из
   `div_ascend`) — прогон на camodel (`--sim`) и на реальном 910B. Аргументы точки входа:
   `x, idx, prefix_sum, y, workspace, tiling` = 6 указателей, 48 байт; `tiling[0..2] = T, M, G`.
2. **`T > 4096`**: `Gather` работает по UB, поэтому сейчас больший `T` отклоняется в `TilingFunc`.
   Варианты — перекладка столбца в workspace (gather по `idx`) и затем сегментная сумма по непрерывным
   диапазонам, либо разбиение `k` по блокам с атомарным сложением в `y`.
3. **Оптимизация**: накопление уже идёт по линиям (4 аккумулятора на группу), так что на тайл приходится
   ~10 векторных операций; дальше — одна свёртка на группу вместо четырёх независимых деревьев и одна
   запись результата на столбец вместо `DataCopyPad` по 8 байт на группу.
